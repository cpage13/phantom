# 003. Token cache persisted across Phantom restart

Phantom's token cache is stored in the disk-backed SQLite alongside buffered uploads, not in process memory only. After Phantom restart (container update, host reboot, crash recovery, power glitch) the cache is reloaded so buffered uploads resume retrying with the last-known token for their `(endpoint, uid)` slot without needing the producer to first make a live request to repopulate. The trade-off is that bearer tokens now live on disk; this is acceptable because the buffered upload payloads themselves contain sensitive data and already require equivalent at-rest protection (file permissions, OS-level filesystem encryption assumed for the host), so a stricter stance on token rest-state would be inconsistent with how the payloads are already handled. Bad tokens that 401 are not silently deleted; they remain in the cache and the corresponding uploads enter the admin-visible `auth_expired` state so an operator can see exactly what credential needs replacement. The admin invalidate surface follows the same rule: `DELETE /v1/admin/tokens/{endpoint}/{uid}` (and the bulk `DELETE /v1/admin/tokens`) marks the slot `status='bad'` and PRESERVES it rather than hard-deleting, so `GET /v1/admin/tokens` keeps surfacing the invalidated slot. The operator-facing invalidate endpoints never hard-delete, and since U6 the cache exposes no hard-delete primitive at all: the lower-level `delete` / `delete_all` pair this sentence used to describe had no consumer, because this decision routed the operator path to the status flip instead.
