# Phantom — Project Context

Phantom is a general-purpose buffering HTTP upload sidecar. The service has zero upstream-specific knowledge; a thin upstream client adapts a specific target API onto Phantom's generic wire protocol.

Producers (or any HTTP client) POST a request chain to Phantom; Phantom acks fast with a synthetic 202 + `ChainResponse`, persists the body locally, and runs the actual upstream calls in the background with retries and token refresh. Three runtime properties matter:

- **Transparent on the wire.** Bytes Phantom forwards to upstream are byte-identical to what the agent sent. Dual SHA-256 hashes per `body_ref` (`body_hash` of raw bytes; `storage_hash` of stored encoded bytes) enforce this — the sender verifies both before forwarding and aborts to the `corrupted` terminal state on mismatch.
- **Always-encode.** One configured codec per deployment (default zstd). No size short-circuit, no `Content-Encoding` pass-through, no per-request opt-out. `PassthroughCodec` (storage token `"original"`) is an explicit operator choice for deployments that want zero codec overhead.
- **Crash-safe.** `asyncio.TaskGroup` at the composition root crashes the process visibly on unhandled worker exception (orchestrator auto-restarts). Persisted rows survive the restart. A startup recovery sweep purges any disk row with `committed=0` and quarantines committed rows whose body files vanished.

## Naming (authoritative)

The naming convention is fixed by this table. CONTEXT.md is authority — any drift in code or docs is a defect.

| Concept | Name | Type |
|---|---|---|
| The chain's identity (= row's primary key) | `chain_id` | `UUID` |
| The credential cache axis | `uid` | `str` |
| Query grouping (admission stores the supplied value, else chain_id; every upload is a group of one) | `group_id` | `UUID` |
| Multi-file association (NULL means standalone) | `multifile_id` | `UUID`, nullable |
| Recorded position within a multi-file set (display only, never enforced at delivery) | `send_order` | `int` |
| Delivery stamp (set once on confirmed delivery, never moved) | `sent_at` | `datetime`, nullable |

The wire header for the credential cache axis is `X-Phantom-Uid`. The admin URL `GET /v1/admin/tokens/{endpoint}/{uid}` carries `uid` as the cache axis path parameter — distinct from `GET /v1/admin/chains/{chain_id}`, which carries chain identity.

## Concept index

### Components

- **`phantom`** (the service; distributed on PyPI as **`phantom-service`** — the bare `phantom` name was taken; the import name is unchanged) — generic buffering HTTP proxy. One Docker container per producer. Opaque at HTTP layer; zero upstream-specific knowledge. Owns the wire protocol, every model, every header, every error code.
- **`phantom-client`** — universal Python SDK over the service's HTTP surface. Two runtime deps: `httpx`, `pydantic`. Publishable to public PyPI.
- **`phantom-emulator`** — test emulator with generic upstream-shaped endpoints (`POST /v1/files/create`, `PUT /v1/files/upload/{token}`, OAuth2 token mint) plus controllable failure injection. It imitates a realistic upstream protocol shape without being tied to any one upstream.
- **`phantom-deploy`** — AWS CDK Python for cloud-side deployment (out of scope for the producer-side architecture).

### Auth & tokens

- **Token cache** — `dict[(endpoint, uid), Authorization]`. Persistent across Phantom restart. → [docs/adr/002-token-cache-keyed-by-endpoint-and-uid.md](docs/adr/002-token-cache-keyed-by-endpoint-and-uid.md), [docs/adr/003-persistent-token-cache.md](docs/adr/003-persistent-token-cache.md).
- **Endpoint** — upstream target identified by hostname (e.g., `files.upstream.example`). Primary axis of the cache key.
- **Credential identifier (`uid`)** — opaque caller-supplied string distinguishing identities at the same endpoint. Phantom never parses it. Avoid the aliases "user id" (too narrow — also covers SP identities) and "token id" (suggests Phantom parses tokens, which it does not).
- **AD-mint capability** — when an instance's `ad_mint` config block is set (typed `AdMintConfig`), Phantom autonomously mints Azure AD client-credentials tokens via its own app registration and writes them to the (endpoint, uid) cache. When `ad_mint` is absent, Phantom waits for the client to push tokens via the `Authorization` header on ingress. The (endpoint, uid) cache is the single source of truth for retry tokens either way.
- **`auth_expired`** — admin-visible state for a buffered upload whose cached token 401s without successful refresh. Surfaces in admin API so an operator can see "this is the only token I have for this slot, and it's bad."

### Topology and storage

- **Instance** — a configured upstream-target within a Phantom process. One Phantom container hosts N instances; each has its own ID, storage partition, and optional `AdMintConfig`. Inbound requests are dispatched by target URL prefix to the matching instance; unmatched targets are rejected with 421. → [docs/adr/006-multi-instance-topology.md](docs/adr/006-multi-instance-topology.md).
- **Two SQLite databases per instance (deliberate)** - `uploads.db` (the `uploads` + `idempotency_index` tables) and `token_cache.db` (the persistent token cache) sit side by side in `<data_dir>/<instance.data_dir>/`. SQLite serializes writers per database file, so the split keeps token reads and writes off the hot uploads writer lock; a token is shared across many uploads, so its lifecycle is independent of any one row. `uploads.db` carries one serialized writer connection plus a dedicated read-only connection for admin and SDK reads; the token cache runs `synchronous=FULL` on its own connection. `schema.sql` also declares a `token_cache` table inside `uploads.db`; that copy is empty in production and the duplicate DDL is deliberate (the cache applies its own copy to its own file). The pre-Phase-1 two-TIER design (a `:memory:` + disk pair with identical schemas) stays gone, as do the `committed` + `tier` columns. → [docs/adr/030-two-database-design.md](docs/adr/030-two-database-design.md), [docs/adr/029-read-only-admin-connection.md](docs/adr/029-read-only-admin-connection.md).
- **`body_location`** — column on `uploads`; ENUM(`ram`, `file`). Records where a row's body bytes live. Single durability commit point — flipped only by the `PersistController`. Replaces the pre-Phase-1 `tier` column + `committed` flag.
- **`BodyStore`** — Protocol governing body storage. Three concrete bindings: `RamBodyStore` (RAM dict), `FileBodyStore` (disk via atomic rename + fsync of file AND parent dir), `HybridBodyStore` (composes Ram + File; RAM-presence-authoritative reads). `Settings.body_store.mode` (`hybrid` / `all_ram` / `all_disk`) selects which binding is wired at the composition root (`app.py`'s lifespan, via the one shared `build_body_store` mode table in `runtime/startup_checks.py`). All three modes are first-class production modes. **Mode-flip guard (back-up-and-run):** `check_body_store_mode` (`runtime/startup_checks.py`, run per-instance by the lifespan before that instance's store opens) no longer refuses to boot. If `all_ram` is selected on an instance whose `<data_dir>/<instance.data_dir>/bodies/` root still holds body files from a prior disk-backed mode, booting `all_ram` there would condemn those rows to `corrupted` (RAM-only recovery can't see disk bytes) and leak the files (no janitor in `all_ram`); so instead of raising, the guard relocates the live DB and body tree to a recoverable mode-switch backup (the flat timestamped siblings described under "Quarantine") and boots fresh, loudly (a WARNING plus the `mode_switch_backup_total` counter). The backed-up data shows up in the quarantine inventory with `reason=mode_switch` and is moved back by the one-call admin restore. To restore service in a disk-backed mode, set `hybrid` or `all_disk` and restart. → [docs/adr/025-never-refuse-to-boot-on-recoverable-config.md](docs/adr/025-never-refuse-to-boot-on-recoverable-config.md).
- **`PersistController`** — the SOLE writer of the `body_location='ram' → 'file'` transition. Migrates RAM bodies to disk on retry-linger (default 90 s) or RAM-pressure breach. Commit-last-column ordering — body files + parent dir fsync'd BEFORE the `UPDATE body_location='file'` commits.
- **Commit-last-column ordering** — the persist-handoff invariant. The flip of `body_location` to `'file'` is the durability commit point; everything that gives the file its persistent guarantees (write, fsync, parent-dir fsync) MUST run BEFORE the column UPDATE commits. Enforced three ways: code-review checklist + pre-commit grep (`scripts/check_persist_ordering.py`) + InvariantAuditor row walk.
- **`BodyOrphanJanitor`** — periodic worker that walks `FileBodyStore.list_orphans()` and deletes body files whose `chain_id` is absent from `uploads`. Closes C1 + invariant #4. Cadence configured via `body_store.body_orphan_sweep_seconds` (default 3600).
- **`RamPressureWatcher`** — periodic worker that polls `RamBodyStore.total_bytes()` against `body_store.ram_ceiling_bytes` and signals the `PersistController` when over ceiling (oldest body migrated first). Cadence via `body_store.ram_pressure_poll_seconds` (default 1.0). The ceiling is an **enforced** bound, not a best-effort gauge: a candidate mid-attempt is skipped only while its attempt is *fresh* (started within ~2× the poll interval); an attempt stalled longer than that (slow/unreachable upstream) is enqueued anyway, so a slow upstream cannot pin the oldest RAM rows in `attempting` and let RAM blow past the ceiling unbounded. Migrating a stalled-attempt body is safe — the `HybridBodyStore` fsyncs to disk before deleting RAM, so the sender's RAM-first read falls back to disk.
- **`InvariantAuditor`** — periodic row walk (Phase 3) that actively asserts invariants #1 and #3 from § 5 of `docs/architecture-intent.md`; bumps `invariant_violation_total` (labeled by invariant) on hits. The other five invariants are counter/gauge monitored — see the architecture-intent reliability-invariants table.
- **`MetricsRegistry`** — in-process counter + gauge registry (`observability/metrics.py`). Surfaced via `GET /v1/admin/observability/counters` + `/gauges` + `/ram_pressure`. No external dependency.
- **Quarantine / backup** - the act of relocating an instance's live DB and body tree to recoverable, set-aside copies, driven by a `reason` discriminator (`storage/integrity.py`). The destinations are NOT a nested `quarantine/<timestamp>/` folder; they are FLAT stamped siblings written directly in the instance data_root (`<data_dir>/<instance.data_dir>/`, whose live `uploads.db` / `bodies` layout is owned by `instances.context.InstanceStoragePaths`). For `reason=corrupted` the siblings are `uploads.corrupted.<stamp>.db` and `bodies.quarantine.<stamp>/`; for `reason=mode_switch` they are `uploads.mode_switch.<stamp>.db` and `bodies.mode_switch.<stamp>/`. The `<stamp>` token (the `%Y%m%dT%H%M%SZ` display iso plus the first 8 hex chars of the backup's `backup_id`) is display and filename-uniqueness material ONLY: a backup's identity is its uuid `backup_id`, recorded with both artifact paths in a `backup.<backup_id>.manifest.json` written (temp-then-rename) before any artifact moves. Two paths produce these: (1) the startup integrity-check gate (Phase 4), run per-instance by the lifespan via `run_integrity_gate` before that instance's store opens; on `PRAGMA integrity_check` failure it backs up with `reason=corrupted`, bumps `db_quarantine_total`, and boots fresh (`db_integrity.fail_open=true` default; `fail_open=false` aborts startup after the backup). (2) the back-up-and-run mode-flip guard, which backs up with `reason=mode_switch` and bumps `mode_switch_backup_total` (see "BodyStore"). A mode_switch backup writes an in-progress marker (`.backup_move.in_progress`, keyed on `backup_id`) so a crash mid-backup is finished forward by `reconcile_interrupted_backup_move` on the next boot via the manifest's declared paths; corruption needs no marker (the corrupt DB on disk is its own re-trigger). Inventory is queryable via `GET /v1/admin/quarantine?instance=<id>` (instance optional; omitted aggregates across every instance; one manifest-driven entry per backup, with unmanifested artifacts flagged as never-restorable anomalies); a chosen `mode_switch` backup is moved back into the live tree by the one-call `POST /v1/admin/quarantine/restore?backup_id=<backup_id>&instance=<id>` (clobber-safe, restart-required), not automatically on boot. → [docs/adr/025-never-refuse-to-boot-on-recoverable-config.md](docs/adr/025-never-refuse-to-boot-on-recoverable-config.md), [docs/adr/026-backup-identity-and-manifest-pair.md](docs/adr/026-backup-identity-and-manifest-pair.md).
- **Transient-lock classifier** — `is_transient_lock_error(exc)` in `storage/sqlite_store.py`: the single shared rule for "this `sqlite3.OperationalError` is a ride-it-out `SQLITE_BUSY`/`SQLITE_LOCKED` contention, not a permanent fault." Deliberately narrow (matches only known lock-message fragments; a schema/type `OperationalError` is left unclassified). Both admission (→ clean `503 storage_unavailable`) and recovery boot (→ bounded retry-with-backoff) consult the one definition so they cannot drift. The SQLite `busy_timeout` (1000 ms) is the cross-process window the classifier's lock case outlasts. → [docs/adr/023-transient-lock-classifier.md](docs/adr/023-transient-lock-classifier.md), [docs/adr/021-busy-timeout-tuning.md](docs/adr/021-busy-timeout-tuning.md), [docs/reliability.md](docs/reliability.md).
- **Persist linger** — retry-linger trigger for the `PersistController`. `body_store.linger_seconds` (default 90). A RAM body whose row has not reached a terminal state within this window migrates to disk.
- **RAM pressure** — ceiling-breach trigger for the `PersistController`. `body_store.ram_ceiling_bytes` (probe-filled when unset). When `ram_body_store_bytes > ram_ceiling_bytes`, the `RamPressureWatcher` signals the controller to migrate the oldest body.
- **Body size threshold** — size-aware persist bypass. `storage.persist_trigger.body_size_threshold_bytes` (probe-filled when unset). In hybrid mode, admission enqueues against the `PersistController` immediately (skipping linger) for bodies whose stored size is at or above the threshold. Pin to 0 to disable.
- **Reaper** — periodic coroutine that deletes terminal-state rows per the retention YAML. Iterates `succeeded`, `failed`, `cancelled`, `stored`, `corrupted`, `auth_expired` on the same sweep.
- **Retention** — per-terminal-state, with metadata-vs-body retention separated. `RetentionCfg` carries a `<state>_metadata_seconds` and `<state>_body_seconds` pair for each terminal state.

### Request mechanics

- **Request chain** — Phantom accepts an envelope describing N HTTP steps with JSONPath capture from each response and `{{step.var}}` substitution into later steps; binary blobs ride as named `body_refs`. → [docs/adr/009-request-chain-envelope.md](docs/adr/009-request-chain-envelope.md), [docs/adr/010-request-chain-envelope-schema.md](docs/adr/010-request-chain-envelope-schema.md).
- **Captured values** — response fields extracted per a step's `capture` directive (named JSONPath with optional `ttl_seconds`) and stored on the upload row. Used both for plumbing later steps and as the queryable record of upstream-assigned identifiers (like the upstream's real `file_id`) for the duration of retention.
- **Capture re-execution** — per-instance YAML knob controlling whether Phantom re-runs the producing step when a captured value expires before later steps need it. Default `false` is safe for upstreams whose idempotency support is unverified. → [docs/adr/011-capture-expiry-reexecution.md](docs/adr/011-capture-expiry-reexecution.md).
- **Local UUID** — a UUID the upstream client generates per upload, used as the synthetic `FileInformation.id` returned to the producer immediately (no wait for upstream reachability). Travels as `metadata.key_value_store["phantom_local_uuid"]` on the upstream request for forward-correlation.
- **Dual body hash** — every body_ref on every UploadRow carries `BodyHashes(body_hash, storage_hash)`. `body_hash` = SHA-256 of raw bytes; `storage_hash` = SHA-256 of stored encoded bytes. Sender verifies `storage_hash` before decode, `body_hash` after decode; mismatch transitions to `corrupted` (terminal). → [docs/adr/014-dual-body-hash.md](docs/adr/014-dual-body-hash.md).

### Operational shape

- **Composition root** — `app.py`'s FastAPI `lifespan` (`phantom.app.create_app`) is the SOLE construction site for every long-lived coroutine; it supervises them under one `asyncio.TaskGroup`, runs the boot-time guards first (`runtime/startup_checks.py`), and is the one path production runs (`python -m phantom` → `create_app`). The pre-Phase-1 plan to migrate this into a `runtime/composition.py` root was abandoned; that dead-path `compose_and_run` shim was deleted in the 2026-05-29 refinement (ADR-024). Spawn-site invariant (enforced greppably by `forbid-asyncio-create-task-outside-composition`): every long-lived coroutine is spawned via a `TaskGroup` (`tg.create_task(...)`, supervised); the unsupervised primitives (`asyncio.create_task(`, `asyncio.ensure_future(`, `loop.create_task(`) are forbidden outside the lifespan's one sanctioned `loop.create_task` SIGHUP site. An unhandled worker exception cascades out of the TaskGroup and crashes the process visibly; the orchestrator restarts; persisted rows survive. → [docs/adr/024-app-lifespan-is-composition-root.md](docs/adr/024-app-lifespan-is-composition-root.md).
- **Hot reload** — operational config knobs (retention, saturation caps, codec choice, persist trigger size threshold, capture re-execution, retry params, AD-mint refresh timings) reload via SIGHUP or `POST /v1/admin/reload`. Atomic snapshot swap via `SettingsHolder`. Worker count and instance list still require restart. → [docs/adr/013-hot-reload.md](docs/adr/013-hot-reload.md).
- **State transitions are owned by the sender.** `workers/sender.py`'s `_on_*` handlers ARE the canonical state-transition table. The executor's discriminated-union result types are exhaustive by mypy. There is no separate state-machine module. → [docs/adr/015-state-transitions-owned-by-sender.md](docs/adr/015-state-transitions-owned-by-sender.md).
- **Smart defaults from system probe.** `config/probe.py` reads `psutil.virtual_memory().total`, `shutil.disk_usage(data_dir).free`, and `os.cpu_count()` at startup. `config/defaults.py` derives saturation, storage (including `body_store.ram_ceiling_bytes` and `persist_trigger.body_size_threshold_bytes`), and worker counts from those facts. Operator-supplied YAML values always win.

### Named code structures

- **`UploadRow`** — the persistence-side Pydantic model for one chain. Carries `chain_id`, `group_id`, `multifile_id`, `send_order`, `state`, `body_location` (Phase 1; replaces `tier`+`committed`), `body_hashes: dict[str, BodyHashes]`, `body_size_bytes`, `attempts`, `next_attempt_at`, `last_error`, `captured_values_json`, `received_at`, `sent_at`, `updated_at`, `body_discarded_at` (H4 carve-out).
- **`ChainAdminDetail`** — admin-only Pydantic model returned by `GET /v1/admin/chains/{chain_id}`. Includes `chain_id`, `state`, `body_location`, `last_step_completed`, `captured`, `attempts`, `last_error`. Distinct from the wire-facing `ChainResponse` (which is the ingress-time 202 body). Lives in both `phantom.models.admin` and `phantom_client.models.admin`; intentionally outside the byte-equality contract test (ADR-012).
- **`AdmissionResult`** — discriminated union returned by `SaturationGate.admit(declared_bytes)`. Variants: `AdmissionGranted`, `AdmissionRefusedSaturation`, `AdmissionRefusedDiskPressure`. The route dispatches via `isinstance`; the typed union forces an exhaustive match (mypy).
- **`AdmissionOutcome`** — return type of `routes/admission.admit_chain`. Carries `row: UploadRow` + `status_code: int` (202 for new admission, 200 for idempotency replay). The H7 closure makes `admit_chain` atomic: row INSERT + idempotency-claim INSERT in ONE SQLite transaction.
- **`ChainStepResult`** — discriminated union returned by `chain.executor.ChainExecutor.execute_one_step`. Variants include `Succeeded`, `Failed5xx`, `FailedAuth`, `BodyMissingError`, `CaptureExpiredRewind` (per ADR-011). Exhaustive by mypy; sender's `_on_*` handlers ARE the dispatch table (ADR-015).
- **`SettingsHolder`** — atomic-swap registry for the live `Settings` snapshot. `SettingsHolder.get()` returns the immutable snapshot; `SettingsHolder.replace(new)` swaps it atomically under the holder's lock. Workers consult via `InstanceContext.current_settings()`.
- **`InstanceSettingsSnapshot`** — the per-instance immutable view of the live `Settings` (one snapshot per instance, swapped atomically on reload). Workers read on each tick; never mutate.
- **`BodyHashes`** — frozen dataclass `(body_hash: str, storage_hash: str)`. SHA-256 hex digests of raw bytes (`body_hash`) and stored encoded bytes (`storage_hash`). Per-`body_ref`, persisted as JSON in `UploadRow.body_hashes`. See ADR-014.
- **`MachineFacts`** — frozen dataclass holding the result of `probe_machine()`. Inputs to `compute_defaults()` → `ResolvedDefaults`.
- **`ResolvedDefaults`** — frozen dataclass with every probe-derived knob (`max_in_flight`, `max_in_flight_bytes`, `max_disk_bytes`, `large_body_threshold_bytes`, `max_large_in_flight`, `ram_ceiling_bytes`, `body_size_threshold_bytes`, `worker_count`).

## Captured-values redaction

`ChainCapture.sensitive: bool` is the wire-visible structural mechanism for marking a captured value as containing credential-grade data. The upstream `upload_url` (presigned PUT, 7-day TTL) is `sensitive=True`; `file_information` is not.

Redaction contract:

- **Log output** — the `SensitiveCaptureRedactor` log filter (in `phantom.observability.logging`) inspects records for `captures` and `sensitive_captures` extras; values marked sensitive are redacted in-place to `<redacted>` before the formatter sees them. The executor emits captures at DEBUG level only and gates the `extra=...` construction behind `logger.isEnabledFor(logging.DEBUG)` so production INFO deployments pay zero cost.
- **Admin responses** — loopback only (per [docs/adr/004-admin-api-loopback-no-auth.md](docs/adr/004-admin-api-loopback-no-auth.md)). Admin responses surface the raw captured value; redaction is log-only. The justification is that admin callers are by construction on-host operators; the `sensitive` flag controls log-channel behavior, not the persisted record.

## Permitted `Any` sites

The `Any` type is a last resort. mypy strict mode is the target. Every use of `Any` in `src/*/src/` must fall into one of the categories below; new code MUST justify any addition by adding an entry here.

The permitted patterns:

1. **`dict[str, Any]` for genuinely dynamic JSON payloads** — JSON bodies whose shape is determined by the chain's upstream (`ChainBodyJson.value`, captured values, JSONPath extraction targets, FastAPI request/response JSON envelopes, the chain envelope's free-form metadata, AD-mint token endpoints' return shape). The Pydantic v2 ecosystem itself uses this pattern at every dynamic-content boundary. The Pydantic field's `description=` carries the semantic contract; the type carries the structural reality.
2. **`dict[str, Any]` for SQLite parameter dicts** — `sqlite3` accepts `dict[str, object]` parameters and DB-API drivers (aiosqlite included) type the parameter slot as `Any` upstream. `storage/sqlite_store.py`'s `_params_for_insert` helper (line 160) uses this pattern for INSERT/UPDATE parameter binding.

The specific bare-`Any` sites (target ≤ 5):

1. **`src/phantom-service/src/phantom/chain/jsonpath.py:41,71`** — `extract(body: Any, path: str) -> Any` and `substitute(template: str, values: dict[str, dict[str, Any]])`. JSONPath operates on arbitrary JSON; its input and output are constrained only by JSON validity. Specifying a constrained type would lie about the contract.
2. **`src/phantom-service/src/phantom/chain/parser.py:99`** — `_walk_json_for_placeholders(value: Any)`. Walks an arbitrary JSON tree looking for `{{...}}` template placeholders. Same justification as JSONPath.
3. **`src/phantom-service/src/phantom/app.py:376`** — `_SuppressSignalHandlerErrors.__exit__(self, exc_type: Any, exc: Any, tb: Any)`. The context-manager protocol's `__exit__` signature is fixed by CPython; the canonical typing is `type[BaseException] | None, BaseException | None, TracebackType | None` but in practice library users use `Any` to match the upstream protocol idiomatically.
4. **`src/phantom-service/src/phantom/routes/admin.py:799,826`** — `_request: Any  # FastAPI Request — typed as Any to keep imports light`. The FastAPI `Request` type is a heavyweight starlette import; the parameter is unused in the handler body and exists only to satisfy FastAPI's injection signature.
5. **`src/phantom-emulator/src/phantom_emulator/routers/upstream.py:277`** — `_scope_for_policy_lookup(_token: str) -> Any`. The failure-injection scope-key type is determined at runtime by the `FailurePolicy` cache; the lookup interface is opaque by design.

The `dict[str, Any]` pattern at JSON boundaries is not enumerated above because it is the idiomatic pattern at JSON boundaries and counting every usage would obscure the actual bare-`Any` surface. If a future module replaces one of the bare-`Any` sites with a constrained type, this list shrinks.

## Pilot surface area

A minimum-viable pilot configuration exercises the smallest end-to-end Phantom deployment. The pilot's load-bearing surface:

- **Ingress** — `POST /v1/send` with a two-step chain envelope (`create_file` metadata POST + `put_s3` body PUT) and a `body_refs={"body": <bytes>}` multipart submission. Authorization is producer-supplied (Bearer) on the request; Phantom caches it under `(endpoint=files.upstream.example, uid=<JWT sub>)`.
- **Admin (loopback)** — `GET /v1/admin/chains/{chain_id}` returns `ChainAdminDetail` (state, tier, captured values, attempts, last_error); `GET /v1/admin/tokens/{endpoint}/{uid}` exposes cached token slot status (no bearer values surfaced); `GET /v1/admin/status` echoes resolved-default summary and observed machine facts; `POST /v1/admin/reload` triggers a hot reload from YAML.
- **Retention** — succeeded metadata kept for 3 minutes (default) so the captured upstream `file_id` is queryable post-delivery; succeeded bodies dropped on success.
- **Failure modes covered by the pilot's test surface** — 5xx retry on metadata or S3 step, 401 retry with auth_expired → AuthKicker wake, presigned URL expiry (capture TTL elapsed), producer restart, Phantom container crash mid-`persist_now`, saturation cap.

Out of pilot scope: admin authentication (loopback bind IS the auth), GET-side proxying for downstream non-upload traffic, multi-routing across heterogeneous upstreams in a single instance.

## Conventions

- **Nothing is locked by labeling.** Decisions are settled when they survive against every deployment they need to serve. ADRs record settled-pending-validation decisions; the right to revisit them stays open.
- **Phantom's scope is POST/upload buffering only.** GET-side proxying for downstream traffic is not part of Phantom. Admin endpoints under `/v1/admin/` use GET for read operations (status, chain lookup, body retrieval); these are loopback-only and distinct from the producer-side POST ingress that Phantom buffers.
- **Coding standards** (Python 3.14+): full type annotations, `from __future__ import annotations`, `pydantic.BaseModel` at serialization boundaries (every field carries a non-empty `Field(description=...)`), `@dataclass` (or `@dataclass(frozen=True)` for internal data with no reassignment requirement) for internal structured data, `logging.getLogger(__name__)` for operational output (no `print()`), no bare numeric literals in production code.
